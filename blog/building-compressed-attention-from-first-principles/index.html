At inference time, only the last token’s query qtq_tqt​ is needed, not the full QQQ matrix. The model is solely trying to produce oto_tot​, the attention output for the most recently generated token, which is then passed through the remaining layers to predict the next token. Since a new token is generated at each step, both qtq_tqt​ and oto_tot​ change at every iteration.

The key observation is that this is not the case for most of KKK and VVV. The vectors k1,…,kt−1k_1, \dots, k_{t-1}k1​,…,kt−1​ and v1,…,vt−1v_1, \dots, v_{t-1}v1​,…,vt−1​ are fixed, they depend only on tokens that have already been generated and will not change when a new token is appended. Rather than recomputing and reloading the entire KKK and VVV matrices at each step, we can keep them resident in HBM, compute only the new projections ktk_tkt​ and vtv_tvt​ for the newly generated token, and append them to their stored matrix.

This is KV caching. It eliminates the redundant recomputation of KKK and VVV across decoding steps and critically reduces the memory transfers that would otherwise dominate inference latency. This saving becomes increasingly significant as context windows grow longer, which is now a central requirement for modern agentic workloads.

2. Arithmetic Intensity and Bottlenecks

Consider the matrix multiplication Z=X⋅YZ = X \cdot YZ=X⋅Y, with X∈RA×BX \in \mathbb{R}^{A \times B}X∈RA×B and Y∈RB×CY \in \mathbb{R}^{B \times C}Y∈RB×C, so Z∈RA×CZ \in \mathbb{R}^{A \times C}Z∈RA×C.

Arithmetic intensity is defined as:

I=FLOPsBytes movedI = \frac{\text{FLOPs}}{\text{Bytes moved}}I=Bytes movedFLOPs​

Each entry of ZZZ requires BBB multiplications and B−1B-1B−1 additions, giving 2B−12B - 12B−1 operations. Across all ACACAC output entries:

FLOPs=(2B−1)⋅AC=2ABC−AC\text{FLOPs} = (2B - 1) \cdot AC = 2ABC - ACFLOPs=(2B−1)⋅AC=2ABC−AC

In BF16, each element occupies 2 bytes. The total memory traffic for reading XXX, YYY and writing ZZZ is:

Bytes=2(AB+BC+AC)\text{Bytes} = 2(AB + BC + AC)Bytes=2(AB+BC+AC)

The arithmetic intensity is therefore:

Imatmul=2ABC−AC2(AB+BC+AC)=ABCAB+BC+AC−AC2(AB+BC+AC)I_{\text{matmul}} = \frac{2ABC - AC}{2(AB + BC + AC)} = \frac{ABC}{AB + BC + AC} - \frac{AC}{2(AB + BC + AC)}Imatmul​=2(AB+BC+AC)2ABC−AC​=AB+BC+ACABC​−2(AB+BC+AC)AC​

In practice, we will often have terms much bigger then and thus will consequentialy dominate the final result. This is why practionners often use the simplified formula depending on the problem at hand.

Example: Transformer Attention Projection

For example, with transformers, during autoregressive generation (inference) or when processing very small context windows, the effective number of tokens processed concurrently is much smaller than the hidden dimensions of the model.

Let us define the number of tokens as N=b×seqN = b \times seqN=b×seq (where bbb is the batch size and seqseqseq is the sequence length). In the attention mechanism, to compute the Queries, we perform the linear projection Q=XWQQ = X W_QQ=XWQ​.

This elegantly demonstrates why transformer inference is notoriously memory bound. The arithmetic intensity of generating QQQ, KKK, and VVV is effectively bounded by NNN. If you are generating a single token at a time (N=1N=1N=1), your arithmetic intensity sits at approximately 111 FLOP/Byte. Because modern accelerators feature machine balances (Peak FLOPs / Peak Bandwidth) heavily skewed towards compute, often requiring >100>100>100 FLOPs/Byte to reach the peak compute roof, this operation will inevitably hit the memory wall.
